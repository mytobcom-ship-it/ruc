도로이용 과금 알고리즘 플로우차트

갱신판(2026-08-23) — 운영 DB ruc에 이미 구축된 실제 마스터/결과 스키마 (charge-tables.html) 기준으로 재작성했습니다. 이전 판이 가정했던 PRIM_GATE_INFO/PRIM_PARKING_ZONE 신규 설계(roadnet/sql/prim_charge_create.sql)는 폐기되었습니다(doc/README.txt A절). 진입~진출을 짝지어야 판정되는 유형은 CLOSED_ROAD(폐쇄식) 하나뿐이고, SPEED(구간단속)는 게이트 쌍이 아니라 구역(zone) 1행의 시작/종료 노드로 짝짓는 별개 메커니즘입니다(2·3절 비교). 맵매칭 판정에는 실제 구조체 MATCH_LINK_INFO(MessageType.h)의 qwLinkID/qwStNodeID/ qwEdNodeID를 기준으로 표기했습니다.

과금 확정 (prim_chargehand INSERT, charge_yn=Y) 무과금 확정 (charge_yn=N) 예외/미종결 (AUDIT 대상) 세션 상태 갱신

0. 공통 배경 — 2단계 구조

과금 처리는 검증서버(MapMatchSvr)와 과금서버 2단계로 나뉩니다(doc/README.txt H-5). 검증서버는 GPS 배치를 맵매칭하면서 이벤트를 원시 감지해 prim_chargehand에 1행만 INSERT합니다 (금액·범칙금 계산은 하지 않음). 과금서버는 prim_chargehand를 charge_status 기준으로 조회해 기준정보 테이블(base_tollfare/base_tollsection 등)과 조인, 최종 금액·범칙금을 계산해 prim_tollcharge(통행료) 또는 prim_vltncharge(위반)에 확정 INSERT합니다. 1~4절은 검증서버 쪽 원시 판정, 5절이 과금서버 쪽 확정 단계입니다.

1. OPEN (개방식, ZONEKIND=02)

필요 기준정보: base_tollgate(gate_div=M), base_tollfare(tollgate_id, car_type, fare_date) — 요금 조회는 5절(과금서버)에서 수행
쉬운 이름(설계 가정): 본선 게이트 통과 사실만 즉시 기록 (진출 지점·세션 보류 없음)
[정정, 2026-08-06 재확인] 아래 게이트 점(point) 이벤트 모델은 실측 데이터와 맞지 않는 부분이 있습니다. 이전 판에 "from_id=to_id=게이트ID 패턴이 실데이터로 확정됐다"고 적었으나, 이는 소수 샘플만 보고 성급히 일반화한 오류였습니다. prim_chargehand의 개방형(charge_type=1) 293건을 전수 확인한 결과 전혀 다른 패턴이 나왔습니다 — 아래 "실측 결과" 참고. 이 절의 플로우차트는 원래 설계 가정(게이트 점 이벤트)을 그대로 보여주되, 실측과 배치되는 지점을 명시합니다.

실측 결과 — 두 가지 서로 다른 패턴이 섞여 있고, 서로 정합성도 안 맞습니다
  • prim_chargehand(charge_type=1) 293건 전부 dist_m이 채워져 있고 from_id≠to_id(road_link.link_id 형식). 같은 트립 내에서 이전 행의 to_id = 다음 행의 from_id로 체인처럼 연결됩니다 — 즉 "게이트 통과 즉시 1건"이 아니라 맵매칭 링크가 바뀔 때마다(hop) 매번 1건씩 쌓이는 구조로 보입니다.
  • 그런데 같은 트립의 prim_tollcharge(2단계 확정)를 보면 from_id=to_id인 점(point) 형태 행들이 있는데, ID 자체가 prim_chargehand 쪽 링크체인과 전혀 다릅니다 — 두 테이블이 같은 트립을 가리키면서도 서로 다른 근거로 채워진 것으로 보입니다.
결론: prim_chargehand와 prim_tollcharge가 서로 다른 시점에 서로 다른 스크립트로 독립 시딩된 것으로 추정되며(5·7절의 vat_amount 예외, SPEED·PARKING 범칙금 이중패턴과 같은 종류의 문제), 개방형이 "게이트 점 이벤트"인지 "링크 hop 누적거리"인지 현재 데이터만으로는 확정할 수 없습니다. 담당자 확인 전까지 이 절의 플로우차트는 참고용 가정으로만 보시기 바랍니다(7절 이슈 참고).
car_type(차종)은 base_carinfo.device_key = prim_chargehand.device_key로 조인해 가져옵니다(5절 참고) — 이 부분은 개방형/폐쇄형 공통이라 위 불확실성과 무관하게 유효합니다.

2. CLOSED_ROAD (폐쇄식 TOLL, ZONEKIND=03)

필요 기준정보: base_tollgate(gate_div=I 진입/O 진출/B 겸용), base_tollsection(entry_tollgate_id, exit_tollgate_id, car_type, fare_date)
쉬운 이름: 진입 게이트 ID 기억 → 진출 게이트 만나면 (진입,진출) 조합으로 요금표를 그대로 조회 — 거리×단가 계산 없음
기존(폐기된) 설계와의 차이: roadnet/sql/prim_charge_create.sql의 FEE_PER_KM × 거리 계산 방식은 실제 스키마와 맞지 않습니다. base_tollsection은 (진입 게이트, 진출 게이트, 차종, 적용일) 조합마다 이미 확정된 정액 toll_fare를 갖고 있어, 거리 계산 없이 조합 조회만으로 요금이 나옵니다. base_tollgate엔 진입-진출을 미리 짝짓는 컬럼이 없으므로, 세션엔 진입 게이트 ID 하나만 기억해뒀다가 진출 게이트를 만난 시점에 두 ID로 base_tollsection을 조회합니다.
[이슈, 2026-08-06] 휴게소 장시간 정차(시동 OFF) 시 진입정보 유실 위험 — 진입정보가 인메모리 세션(TRIP_ID 단위)에만 있고 DB엔 없어서, 기본 TTL(ttl_sec 기본값 3600초=1시간, ConfigDefaults.h:29) 보다 오래 정차하거나(TTL 만료로 세션 소실) 시동 재시작으로 TRIP_ID가 아예 바뀌면(수집앱 동작 방식에 따라 다름, 확인 필요) 진출 게이트 통과 시 요금이 부과되지 않을 수 있습니다. 아래 플로우차트의 보라색(신규) 노드가 대응방안입니다 — ① 진입 시 세션과 DB에 동시 기록(durable) ② 진출 판정 시 TRIP_ID 세션뿐 아니라 DEVICE_KEY 기준 미종결 기록도 함께 조회 ③ CLOSED_ROAD 전용 장기 TTL 분리 ④ 그래도 못 찾는 영구 미종결 건은 일 단위 배치로 스윕해 AUDIT 처리.

"이번 구간 이동거리"는 맵매칭된 링크 경로 기준 누적값으로 계속 기록은 하지만, 실제 요금은 base_tollsection.toll_fare를 그대로 쓰므로 요금 산출에는 쓰이지 않습니다. 다만 prim_chargehand.dist_m 컬럼 코멘트는 "폐쇄식 요금 산출 기준"이라 적혀 있어 실제 의도와 상충합니다 — 재작업 시 확인 필요(7절 7번). 진입-진출 조합이 base_tollsection에 없는 경우 (미등록 조합) 처리 정책도 아직 정해지지 않았습니다(7절 6번).
실제 DB의 기존 데이터에서 from_id=진입 tollgate_id, to_id=진출 tollgate_id 패턴이 그대로 관측돼 이 절의 설계가 실측과 일치함을 확인했습니다.
트레이드오프: README F절의 "핫패스(매 GPS)에서 DB 왕복 최소화" 원칙과 배치되는 것처럼 보이지만, DB 기록은 진입 이벤트당 1회뿐이라(매 GPS 아님) 기존 배치 UPDATE보다도 훨씬 적은 볼륨입니다.

3. SPEED (구간단속, ZONEKIND=04)

필요 기준정보: base_mapinfo(zone_kind=04, f_node/t_node 또는 link_id, speed_limit_kmh)
쉬운 이름: 구역 시작노드 진입 기억 → 종료노드 도달 시 평균속도 계산 → 제한속도 초과 여부 확정
폐쇄식과 다른 점: 게이트 2건(진입/진출)을 별도로 등록하는 폐쇄식과 달리, 구간단속은 base_mapinfo 1행이 f_node(시작)·t_node(종료)를 동시에 갖습니다. 세션엔 "어느 zone_id로 진입했는지"만 기억하면 됩니다.

4. PARKING (주정차, ROAD_KIND=4)

기준정보: ruc.base_roadlink(road_kind='4', geom_type='POLY', coords jsonb 폴리곤). 구현: RawLogWorker.cpp::ProcessParkingCharge() / AppendExpiredParkingCharge(). config: [charge] park_buf / park_entrycnt / park_speedmax / park_exitcnt / park_regrace / park_ttl

RAW_VLD=false 행도 주정차 판정은 수행합니다(2026-08-22 사용자 확정). 차가 멈추면 GPS 가 측위를 놓쳐 정확도가 급격히 나빠지는데(실측: DRIVE_STATUS=PARKED 497건 평균 64m, ON_ROAD 는 7m), 하필 주정차 판정이 가장 필요한 순간이 그때입니다. 이 행들을 버리면 도착 정차가 통째로 누락됩니다 — 실측에서 어떤 트립의 도착 정차 17점·79초가 전부 RAW_VLD=false 였습니다. 맵매칭(다른 3종 과금)은 종전대로 SKIP 합니다: 좌표를 링크에 붙이는 일은 정확도가 필요하지만, "폴리곤 안에 있었나"는 훨씬 큰 공간 판정이라 성격이 다릅니다.

6. 세션 확장 필드 정리

CLOSED_ROAD·SPEED·PARKING은 VEHICLE_TRIP_SESSION(RawLogWorker.h)에 아래 필드 추가가 필요합니다. 트립 단위로 유지되며, ExpireTtlSessions() 만료 시 "진행 중" 상태가 남아있으면 각 절의 미종결(AUDIT) 분기로 처리합니다. OPEN은 점 이벤트라 세션 보류가 없어 표에 없습니다.
유형세션 필드(안)용도
OPEN 해당 없음 GPS 1건으로 즉시 확정되므로 세션 보류 불필요
CLOSED_ROAD bInClosedRoad, strEntryTollgateId, dtClosedEnter, dfClosedAccumDist(참고/감사용) 진입 게이트 ID만 기억 — 진출 시점에 현재 게이트 ID와 조합해 base_tollsection을 바로 조회 (진입-진출을 미리 짝짓는 GATE_PAIR_ID류 필드는 불필요 — base_tollsection PK 자체가 조합 키).   7. base_mapinfo.zone_kind 실제 저장 형식이 문서 코멘트와 다름 — 컬럼 코멘트는 "01~05"라 적혀있지만 실측 데이터는 앞자리 0 없는 '1'/'2'로 저장돼 있음(1글자). 04/05 등록 시 WHERE zone_kind='04'가 아니라 '4'일 가능성 — 실제 등록 전 재확인 필요.
  8. vat_amount=0 예외 75건(전체 436건 중) — 부가세 10% 공식과 맞지 않는 기존 데이터가 일부 있어 100% 확정 규칙은 아님(5절).
  9. HYBRID 게이트 미반영 — 진입 즉시 소액 정액 + 최종 진출 거리요금을 동시에 부과하는 IC 케이스. base_tollgate.gate_div가 한 지점당 값 하나만 가져 못 담음(doc/README.txt D절).
  10. base_tollsection에 없는 (진입,진출) 조합 발생 시 처리 정책 미정 — 무과금 처리할지 AUDIT으로 남길지 결정 필요(2·5절).
  11. prim_chargehand.dist_m이 폐쇄식 요금 산출에 실제 쓰이는지 컬럼 코멘트가 상충 — base_tollsection 고정요금 구조와 "폐쇄식 요금 산출 기준"이라는 코멘트가 맞지 않음. 확인 필요(2절).
  12. nDriveStatus/DRIVE_STATUS_PARKED가 RawLogWorker.cpp에서 아직 미사용 — 정차 감지 자체가 코드에 없는 상태(4절).
