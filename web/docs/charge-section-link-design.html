개방형·폐쇄형 과금 구간 — 링크 판정 설계

"지금 맵매칭된 링크가 개방형·폐쇄형 과금 구간(게이트)에 해당하는가"를 판정하기 위해 필요한 컬럼을 설계합니다. 원칙은 기존 4개 테이블(base_roadlink/base_tollgate/base_tollfare/base_tollsection)의 스키마를 한 컬럼도 바꾸지 않는 것입니다.

후속 문서 있음: 이 문서(개방·폐쇄형 전용)를 구간단속·주정차까지 포함해 4유형 전체로 확장하고, 브릿지 테이블 제안을 철회한 charge-unified-table-design.html이 이후에 작성됐습니다. 새로 설계를 검토하신다면 그쪽을 우선 참고하세요 — 이 문서는 개방·폐쇄형 세부 근거 자료로 유효합니다.
전제: "게이트 점 이벤트" 모델 기준입니다. charge-tables.html I-7에서 개방형이 정말 "게이트 통과 즉시 1건"인지 "링크 hop마다 누적"인지 실측 데이터로 확정되지 않았다고 정리된 바 있습니다. 이 문서는 원래 설계 가정(점 이벤트)을 따릅니다 — 담당자 확인 후 실제로 hop 누적형이라면 6절 판정 흐름만 교체하면 되고, 아래 테이블 설계 자체는 영향받지 않습니다(어느 쪽이든 "현재 링크 → 게이트/도로 매칭"은 동일하게 필요).

0. 배경·설계 원칙

charge-tables.html에서 이미 확인된 문제: base_tollgate.link_id는 "소프트 참조"라고 코멘트에 적혀 있지만 참조 대상이 road_link.link_id(MapMatchSvr가 실제로 쓰는 표준노드링크)가 아니라 base_mapinfo.link_id이고, 그마저 실데이터 3건 전부 NULL입니다. 즉 지금 매칭된 링크가 과금 게이트/도로에 해당하는지 ID로 조인할 방법이 없습니다.
  1. 컬럼을 늘리지 않는다 — base_tollgate.link_id는 이미 있는 컬럼이다. 참조 대상 정정 + 데이터 백필만 한다.
  2. 신규 테이블은 최소 1개, 그것도 선택사항으로 — 게이트 판정(요금 계산)엔 base_tollgate만으로 충분하다. "지금 이 링크가 어느 과금도로 위에 있는가"라는 구간 소속 질문에만 별도 브릿지 테이블이 필요하다.
  3. 핫패스 DB 왕복 0회 — 기존에 합의된 원칙(doc/README.txt F절, PostgrePool.cpp:264 keepPoolAlive() 패턴)을 그대로 따른다. 게이트/구간 데이터는 MapMatchSvr 프로세스 메모리에 전량 캐시하고, GPS 처리마다 DB를 조회하지 않는다.

참고 — road_link (표준노드링크, 변경 없음)

컬럼타입설명

3. base_tollgate — 변경 후 DDL 불변

컬럼 추가 0건 — 기존 link_id 컬럼 용도 정정 + 데이터 백필만

변경 전

link_id  varchar(20)  DEFAULT NULL
-- 참조: base_mapinfo.link_id (소프트)
-- 실데이터: 3건 전부 NULL

변경 후

link_id  varchar(20)  DEFAULT NULL   -- 타입·컬럼명 동일
-- 참조: road_link.link_id (소프트, 1회성 공간매칭으로 백필)
-- 실데이터: 게이트 좌표(lon,lat) 최근접 링크로 채움
컬럼변경 전 설명변경 후 설명
link_id base_mapinfo.link_id 소프트참조, 전부 NULL road_link.link_id 소프트참조. 게이트 (lon,lat) 기준 road_link.coords 최근접 링크를 1회성 스크립트로 채움. gate_div=M(개방형 본선)·I/O(폐쇄형 입출구) 전부 동일 방식.
왜 컬럼을 안 늘려도 되는가: link_id는 이미 varchar(20)로 road_link.link_id (varchar(10))를 담기에 충분한 길이입니다. "소프트 참조"이므로 하드 FK도 새로 걸 필요 없습니다 (road_link가 road_link.link_id에 대해 UNIQUE 여부가 확인 안 됨 — 확인 전까지 소프트 참조 유지가 안전).
좌표거리 매칭이 유일한 경로일 때의 리스크: 게이트가 매우 짧은 링크 위에 있거나 두 링크 경계에 걸쳐 있으면 최근접 링크가 모호할 수 있습니다. 백필 스크립트는 최근접 1건 + 거리(m)를 같이 출력해, 거리가 큰 행(예: 30m 초과)은 수동 확인 대상으로 별도 표시할 것을 권장합니다.

4. (선택) 신규 base_roadlink_link 신규 선택

표준노드링크 ↔ 과금도로(base_roadlink) 구간 소속 브릿지 테이블
요금 계산 자체에는 필요 없습니다. 개방형은 게이트(M) 통과, 폐쇄형은 입구(I)+출구(O) 게이트 짝만으로 base_tollfare/base_tollsection에서 정액을 바로 조회하므로, "현재 링크가 도로 구간 내부 어디쯤인지"는 금액 산정과 무관합니다 (base_roadlink는 위상 없는 "가상 링크"이고 실제 요금도 이동거리 계산이 아니라는 점이 charge-tables.html에 이미 정리돼 있음).

그럼에도 아래 두 상황에 쓸모가 있어 선택 옵션으로만 제안합니다:
  • 폐쇄형 휴게소 장시간 정차(I-8 이슈) — 진입 게이트 세션이 TTL로 소실됐을 때, "지금 링크가 그래도 이 폐쇄도로(road_id) 위인가"를 보조 판단 근거로 쓸 수 있음 (durable 기록 설계의 보조 데이터, charge-issues.html 참고).
  • 지도 관리 화면 — 관리자가 등록한 과금 구간을 표준노드링크 단위로 하이라이트 표시.
컬럼타입기본값PK/FK설명
road_idvarchar(20)—PK-1 / FK→ base_roadlink.road_id (하드 FK)
link_idvarchar(10)—PK-2 / 소프트→ road_link.link_id (소프트 — UNIQUE 미확인 상태라 하드 FK 보류)
seqintegerNULL—도로 내 진행 순서(선택) — base_roadlink엔 위상(f_node/t_node)이 없어 순번으로만 방향 표현 가능
reg_dtvarchar(14)NOW() 포맷—등록일시(백필 스크립트 실행 시각)
기존 4개 테이블과의 관계: 이 테이블은 base_roadlink/base_tollgate를 참조만 하고 역으로 참조당하지 않으므로, 지워도 기존 과금 판정(게이트 이벤트)에는 영향이 없습니다 — 순수 부가 기능입니다. 우선순위가 낮다면 3절(base_tollgate.link_id 백필)만 먼저 적용해도 개방형·폐쇄형 게이트 판정은 동작합니다.

5. MapMatchSvr 설정값 (DB 아님) 신규

좌표거리 폴백 매칭(링크 ID가 정확히 안 맞을 때 대비)용 임계값입니다. 기존 [mapmatch] 섹션의 radius/radius_min/radius_max/radius_skip과 동일한 네이밍 규칙(짧은 접두사, 밑줄 최대 1개, 단위는 이름이 아니라 주석에)을 따릅니다. 
# config.ini [mapmatch] 섹션 추가안
# gate_radius                      - 게이트 좌표거리 폴백 매칭 반경 m       (기본값 결정 필요, 예: 30)
gate_radius=30
ConfigDefaults.h에 CFG_DEF_GATE_RADIUS 형태로 추가하면 기존 CFG_DEF_RADIUS* 네이밍과 일관됩니다. 실제 기본값(30m 등)은 담당자 확인 필요 — 이 문서는 설계 자리만 마련합니다.

6. 판정 흐름 적용 예시

개방형 (gate_div=M)

  1. MapMatchSvr 시작 시 base_tollgate(use_yn='Y') 전량 SELECT → 인메모리 해시맵 link_id → tollgate_id 구성 (DataLoader.h의 m_mapLinkInfoList 패턴 재사용).
  2. GPS hop마다 매칭된 qwLinkID를 문자열 변환해 해시맵 조회. 히트하면 게이트 통과로 판정.
  3. 미스면 폴백: 매칭 좌표와 캐시된 게이트 lon/lat 간 거리가 gate_radius 이내인 게이트가 있는지 확인.
  4. 확정되면 base_tollfare(tollgate_id, car_type, fare_date≤오늘 중 최신)로 정액 조회 → prim_chargehand 적재 → prim_tollcharge 확정.

폐쇄형 (gate_div=I/O)

  1. 동일한 link_id → tollgate_id 해시맵에서 gate_div도 함께 보유.
  2. 입구(I) 히트 → VEHICLE_TRIP_SESSION에 진입 게이트ID 저장(doc/README.txt G절 GatePairID 명명 참고), durable 기록 여부는 I-8 대응방안 별도 결정.
  3. 출구(O) 히트 → 세션의 진입 게이트ID + 이번 출구 게이트ID + car_type + fare_date로 base_tollsection 조회 → 고정 구간요금 확정.
  4. 4절 base_roadlink_link를 도입했다면, 세션이 없을 때(TTL 소실) "현재 링크가 이 road_id 위인가"로 보조 판단해 I-8 시나리오 완화 가능(선택).

7. 적용 순서

  1. road_link에서 base_tollgate의 (lon, lat) 기준 최근접 링크 + 거리(m)를 산출하는 1회성 스크립트 작성 (SQL ORDER BY point <-> geom LIMIT 1 류 또는 Python haversine).
  2. 결과 검토 — 거리가 큰 행(임계값 초과)은 수동 확인 목록으로 분리.
  3. UPDATE base_tollgate SET link_id = ... — DDL 변경 없이 데이터만 채움.
  4. COMMENT ON COLUMN base_tollgate.link_id IS '...' — 참조 대상 정정(선택, 문서화 목적).
  5. (선택) 4절 base_roadlink_link DDL 실행 + 동일 방식으로 base_roadlink.coords 선분을 따라가며 road_link 후보들을 채우는 배치 작성.
  6. MapMatchSvr config.ini에 gate_radius 추가, ConfigDefaults.h에 기본값 정의 (이후 캐시 클래스·판정 코드는 별도 구현 과제 — doc/README.txt H절 4·5번).

8. 미해결·전제조건

  • I-7 미해결 — 개방형이 정말 "게이트 점 이벤트"인지 자체가 실측과 안 맞는 상태. 이 설계는 점 이벤트 가정 하의 매칭 방법론이며, 담당자 확인 후 모델이 바뀌면 6절 판정 흐름만 재검토하면 됨.
  • road_link 스냅샷 정합성 — road_link 코멘트상 "2025-07-16판". MapMatchSvr가 실제 맵매칭에 쓰는 link.psf(CreateData 생성물)가 동일 시점 데이터인지 확인 필요 — 다르면 같은 도로도 link_id가 다를 수 있어 백필 매칭이 어긋남.
  • gate_radius 값 미정 — 30m는 예시일 뿐, 실제 게이트 근방 표준노드링크 밀도를 보고 정할 것.
  • gate_div=B(겸용) 미관측 — 실데이터 3건 모두 M/I/O만 존재. B 케이스가 실제로 나오면 해시맵에 입구·출구 두 역할을 동시에 매핑하는 처리가 추가로 필요.
  • road_link.link_id UNIQUE 여부 미확인 — 4절 브릿지 테이블의 FK를 하드로 걸지 소프트로 둘지는 이 확인 이후 결정.
