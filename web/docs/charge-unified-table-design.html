과금 4유형 통합 테이블 설계 — 최소 수정안

개방형·폐쇄형·구간단속·주정차 4개 유형 전부가 같은 테이블 구조, 같은 판정 함수 2개로 처리되도록 설계합니다. 기존 운영 테이블은 컬럼 단위로 0건 변경, 신규 테이블도 0개입니다.

"최소 수정"의 의미 재정의: RawLogWorker.cpp엔 과금 관련 코드가 현재 0줄이라(이전 대화에서 grep으로 확인) "기존 코드 보존"이 아니라 "새로 짤 코드량을 유형별로 4배 늘리지 않는 것"이 여기서 말하는 최소화입니다. 4유형이 각자 다른 판정 로직을 타면 코드·테스트·버그가 4배가 되므로, 테이블 설계 단계에서부터 공통 경로로 수렴시키는 게 목표입니다.

0. 목표·원칙

  1. 기존 4대 운영 테이블(base_roadlink/base_tollgate/base_tollfare/base_tollsection) 컬럼 변경 0건 — 지난 설계(charge-section-link-design.html)의 원칙을 그대로 유지.
  2. 신규 DB 테이블 0개 — 지난 설계에서 "선택사항"으로 제안했던 base_roadlink_link 브릿지 테이블조차 이번 통합설계에선 불필요해짐(6절 참고).
  3. 판정 함수는 2개로 수렴 — "구역 진입/이탈 판정" 1개 + "게이트 세부 판정" 1개. 4유형이 이 2개 함수의 조합으로만 구성됨.
  4. 기존 미사용 훅(hook) 재사용 — Server.h:104 m_strChargeInsertSQL, RawLogWorker.h:92 strChargeInsertSQL은 이미 로드 배선까지 돼 있고 실행만 안 됨. 새 배선을 추가하지 않고 이 기존 훅에 실행 코드만 연결.

기존 컬럼 그대로 사용합니다. 핵심은 geom_type에 따라 런타임에서 같은 폴리곤 판정 함수로 수렴시키는 것 — LINE은 폭 zone_radius(m)만큼 버퍼링해 회랑(폴리곤)으로 바꾸고, POLY는 coords를 그대로 폴리곤으로 씁니다. 함수 입장에서는 둘 다 "폴리곤 하나"로 동일합니다.

5. base_tollgate — link_id 백필 (기존 설계 재사용)

이 부분은 이전에 이미 설계한 내용과 동일합니다 — 컬럼 추가 없이 기존 link_id 컬럼(현재 전부 NULL)에 road_link.link_id 값을 백필하고, 폴백으로 lon/lat 좌표거리(gate_radius)를 씁니다. 개방형·폐쇄형에서 Layer 1(도로 진입) 확인 후, Layer 2로 "정확히 어느 게이트인지"를 좁힐 때만 조회합니다.
구간단속·주정차는 이 테이블을 아예 참조하지 않습니다 — Layer 1(폴리곤 진입/이탈)만으로 판정이 끝나기 때문입니다.

6. (철회) base_roadlink_link 브릿지 테이블 — 이번 설계에선 불필요

이전 설계 4절에서 "선택사항"으로 제안했던 base_roadlink_link(표준노드링크 ↔ base_roadlink 매핑 브릿지 테이블)는 이번 통합설계에서 제외합니다.
  • 이유 1: 그 테이블의 원래 목적("현재 링크가 어느 도로 위인지")은 Layer 1의 폴리곤 진입/이탈 판정이 정확히 같은 역할을 합니다 — 링크 단위 매핑 테이블을 미리 만들어 유지보수할 필요 없이, 좌표 자체로 실시간 판정하면 됩니다.
  • 이유 2: POLY(주정차) 구역은 링크와 정렬이 안 맞을 수 있어(주차장처럼 도로망 밖 영역) link_id 기반 매핑 자체가 원천적으로 안 맞는 유형이 있습니다. 좌표 기반 폴리곤 판정이 LINE· POLY 양쪽에 다 통하는 유일한 공통 방법입니다.

7. 공통 판정 로직 (의사코드)

2026-08-10 대화에서 수정됨: 최초안은 "Layer 2는 Layer 1이 히트했을 때만 호출"이었는데, 고속도로 중간에 다른 road_id로 갈아타는 경우(예: 경부→영동) Layer 1의 "현재 zone"이 바뀌면서 진출 게이트를 놓치는 결함이 발견됨. Layer 2(게이트 감지)는 Layer 1과 완전히 독립적으로, 세션의 bInGateRoad 플래그만 보고 매 GPS마다 항상 실행하도록 수정. road_id로 게이트 후보를 좁히지 않고 base_tollgate 전체(개방형+폐쇄형)를 대상으로 조회. 
// Layer 1 — 구간단속·주정차 판정, 그리고 zone_id 라벨링용. 매 GPS 1회
ZoneMatchResult MatchZone(POINT curPos, ZoneCache& cache) {
    for each zone in cache.activeRoadlinks:              // base_roadlink 전량 인메모리 캐시(4유형 전부)
        polygon = (zone.geom_type == LINE)
                    ? BufferLine(zone.coords, cfg.zone_radius)  // 회랑 변환(구간단속)
                    : zone.coords;                              // POLY는 그대로(주정차)
        if PointInPolygon(curPos, polygon):                     // GISUtil::IsCrossSgmt2Sgmt 재사용 가능(교차판정)
            matches.add({ road_id: zone.road_id, road_kind: zone.road_kind });
    return matches;   // 여러 zone이 겹칠 수 있어 배열로 반환(2026-08-10 확정, 8절 참고)
}

// Layer 2 — 개방형·폐쇄형 게이트 감지. Layer 1 결과와 무관하게 매 GPS마다 항상 실행
GateMatchResult MatchGate(uint64 matchedLinkId, POINT curPos, GateCache& cache) {
    if cache.byLinkId.contains(matchedLinkId):                  // O(1) — base_tollgate.link_id 백필 결과, road_id로 안 좁힘
        return cache.byLinkId[matchedLinkId];
    for each gate in cache.gatesNear(curPos):                   // 폴백: 좌표거리, 전체 게이트 대상
        if HaversineMeters(curPos, gate.point) <= cfg.gate_radius:
            return gate;
    return { matched: false };
}

// 매 GPS 처리 시 — Layer 1/2를 각자 독립적으로 호출
zoneMatches = MatchZone(curPos, roadlinkCache);      // 구간단속·주정차 트랙에서 사용
gateMatch   = MatchGate(matchedLinkId, curPos, gateCache);  // 개방형·폐쇄형 트랙에서 사용, 조건 없이 항상 호출
PointInPolygon은 신규 구현이 필요하지만(charge-issues.html에서 이미 "미구현"으로 확인됨), 기존 GISUtil::IsCrossSgmt2Sgmt/IsCrossSgmt2Grid(선분 교차 판정)를 레이 캐스팅 알고리즘의 내부 연산으로 재사용할 수 있어 완전 처음부터 짜는 것보단 작업량이 줄어듭니다. HaversineMeters는 이미 RawLogWorker.cpp:1150에 구현돼 있어 그대로 재사용합니다.

9. 유형별 기반정보 + PRIM_CHARGEHAND 예제

9-1. 우리 코드(MapMatchSvr)가 조회하는 기반정보 vs 다운스트림(과금서버) 범위

MapMatchSvr의 역할은 prim_chargehand까지만입니다(지난 대화 결론) — 실제 요금·범칙금 산정 테이블은 이미 운영 중인 별도 과금서버가 참조합니다. 이 경계를 명확히 하기 위해 "우리가 실제로 SELECT하는 테이블"과 "다운스트림만 쓰는 테이블"을 나눠 표시합니다.

9-2. zone_id 결정 규칙 (2026-08-10 확정)

한 트립이 여러 road_id를 거칠 수 있는 경우(경부→영동처럼) zone_id는 진입 시점에 확정된 road_id로 고정합니다 — 이 컬럼은 참고·표시용일 뿐 요금 계산에 안 쓰이므로 (9-1절), 정확성보다 "항상 같은 규칙"이 우선입니다.

10. 이 설계로 얻는 것

  • 구현할 신규 함수 2개(MatchZone, MatchGate) — 유형별로 4벌 안 짜도 됨
  • DB 스키마 변경 0건 — 신규 테이블·신규 컬럼 없음, 기존 link_id 백필 하나뿐
  • 테스트 격리 용이 — base_roadlink 1행 + (필요시) base_tollgate 2행만으로 4유형 전부 테스트 가능(지난 대화의 "임시 격리 데이터" 원칙과 그대로 호환)
  • 기존 미사용 훅 재사용 — strChargeInsertSQL 로드 배선이 이미 있어 새 설정 항목을 안 만들어도 됨

11. 미해결 전제조건

  • I-7 미해결(개방형 점 이벤트 vs 링크 hop 누적) — 이 설계는 점 이벤트 가정. 모델이 바뀌면 Layer 2만 재검토.
  • zone_radius(LINE 버퍼 폭)·gate_radius 실값 미정 — 자리만 마련.
  • PointInPolygon 신규 구현 필요(4절에서 짚은 재사용 가능 부분 있음).
  • 코드체계 변환표 필요 — base_roadlink.road_kind(0-base)와 prim_chargehand.charge_type 값이 우연히 유사하지만 공식 매핑표는 없음(charge-tables.html 0-1절 "코드체계 3종 불일치" 참고).
  • 주정차 nDriveStatus 배선(RawLogWorker.cpp에서 아직 안 읽힘)은 이 테이블 설계와 별개로 필요.
