과금 6유형별 PRIM_CHARGEHAND 컬럼 값 비교 v1.8 문서 기준 갱신

행 = 컬럼, 열 = 과금 유형. 초판은 RUC_위치검증서버_테이블설계서_v1.8.docx(문서번호 RUC-DB-LOC-2026-001, 작성 2026.06, 에스트래픽㈜)와 charge-unified-table-design.html 9-3절 예시값을 근거로 작성했으나, 2026-09-15 자로 표의 모든 값을 실제 구현 코드와 로컬 ruc DB 실데이터 163행으로 재검증해 정정했습니다. 설계 문서와 구현이 다른 부분은 구현이 기준입니다 (설계안 쪽 차이는 9-3절 상단 정정 안내 참고).

[해결됨, 2026-08-12 재확정] 개방형은 게이트 통과 시 요금 부과(점 이벤트)가 맞습니다 — "링크 hop마다 누적"이 아닙니다. 실측 prim_chargehand 293건에서 관측된 "링크 hop 체인" 패턴(from_id≠to_id가 연속 행에서 이어지는 형태)은 정상 동작이 아니라 잘못 시딩된 데이터로 판단됩니다 (doc/README.txt I-7에서 이미 "prim_chargehand·prim_tollcharge가 서로 다른 시점에 독립적으로 시딩된 것으로 추정"이라 의심했던 것과 일치).

v1.8 문서에 TOLLGATE_ID/ENTRY_TOLLGATE_ID/EXIT_TOLLGATE_ID **전용 컬럼**이 별도로 있는 것 자체는 유효한 발견입니다 — 개방형은 TOLLGATE_ID에 통과한 게이트ID가 들어갑니다. 다만 FROM_ID/TO_ID가 "링크/노드 ID 전용"이라는 이전 결론은 재검토 필요 — 기존 설계(from_id=to_id=게이트ID)와 이 표의 값(아래 게이트 그룹 참고)이 실제로 어떻게 공존하는지는 아직 미확인입니다.
[미확인, 중요] v1.8 문서(4절)는 "과금서버가 settings.ini 요율로 직접 계산"이라고 명시하는데, 오늘까지의 설계 전체(charge-tables.html 등)는 base_tollfare/ base_tollsection/base_fare DB 테이블 조회 기반이었습니다. 두 기준 중 어느 쪽이 최신/맞는지 담당자 확인 필요 — 이 문서의 표는 일단 v1.8(컬럼 정의)을 그대로 반영했지만, 요금 계산 로직 자체는 재검증이 필요합니다.
[해결됨 — 2026-09-15 실측 확정] 이 자리에 원래 "일반도로의 CHARGE_UNIT 선택 기준이 문서에 없어 미확정, 다른 4유형은 전부 0(NODE) 고정" 이라고 적혀 있었으나 둘 다 사실이 아닙니다. 일반도로는 0(NODE) 고정으로 구현돼 있고(실데이터 107행 전부 0), 나머지 유형도 "전부 0" 이 아니라 유형마다 다릅니다 — 0·1 → 0(NODE), 2·3·5 → 1(LINK), 4 → 2(POLYGON). 값 2(POLYGON)는 이 문서에 정의조차 없었습니다.
문서 자체의 오류로 보이는 부분: v1.8 3.1절 ⑦단계가 "BASE_CUSTINFO 조인 → VEHICLE_TYPE 확인"이라고 하는데, BASE_CUSTINFO엔 DEVICE_KEY도 VEHICLE_TYPE도 없습니다. DEVICE_KEY+CAR_TYPE을 가진 건 BASE_CARINFO입니다 — 원문서 오타로 추정, 여기서는 BASE_CARINFO 기준으로 표기.
