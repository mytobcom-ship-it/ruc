TRIP_EVENT 이상 데이터 조사 요청

위치검증서버(맵매칭·과금) 측에서 수신 데이터를 전수 점검하던 중, 수집 단계에서 생성된 것으로 보이는 TRIP_EVENT 이상 4건을 확인했습니다. 위치검증서버에서는 보정이 불가능한 영역이라 확인을 요청드립니다.
점검 대상: 로컬 검증 DB ruc.prim_rawgps 의 실수집 데이터 36개 트립 / 8,344 틱 (2026-09-15 기준)

1. 점검 범위 — 합성 데이터 제외

집계에서 제외한 데이터가 있습니다. 이 DB 에는 위치검증서버 측 알고리즘 시험용으로 만든 합성 시드 데이터가 섞여 있습니다 — 단말 CAR000197(차량번호 000093), 22개 트립 / 473 틱. 좌표 증분이 완전히 일정하고 속도가 톱니파 형태라 실제 수집 데이터가 아닙니다. 수집서버에서 생성한 데이터가 아니므로 아래 집계에서 전부 제외했습니다. (전체는 58트립/8,817틱이며, 그중 실수집분이 36트립/8,344틱입니다.)

2. 먼저 — 정상 패턴 정의

실수집 36개 트립 중 32개(89%)가 아래 규칙을 정확히 지키고 있어, 이것을 정상 규격으로 보았습니다.

운행 종료 틱(TRIP_EVENT=2)의 규격
  1. 트립 스트림의 맨 마지막에 1건만 존재한다.
  2. 직전 틱(GPS_SEQ −1)의 복사본이다 — GPS_DT·GPS_LAT·GPS_LON·SPEED_KMH가 모두 같다.
    실수집 종료 틱 37건 중 36건이 이 규칙을 지키며, 유일한 예외가 아래 유형 ② 그 자체입니다.
  3. DRIVE_STATUS는 종료 표식으로 2가 찍힌다(합성분 포함 종료 틱 59건 전부 해당 — 직전 틱과 값이 달라도 정상이므로 이상 징후가 아니다).

운행 시작 틱(TRIP_EVENT=0)은 전수 정상이었습니다(각 1건, 항상 첫 틱 — 합성분 포함 58트립 전부). 이상은 종료 쪽에만 있습니다.

8. 확인 요청 사항

  1. 종료 판정 조건 — 정차(SPEED_KMH=0) 지속을 운행 종료로 보는 로직이 있는지, 있다면 임계값은 얼마인지. 유형 ① 2건 모두 정차 상태에서 발생했습니다.
  2. 조기 종료 후 재시작 처리 — 종료를 보낸 뒤 같은 트립의 데이터가 계속 발생하면 수집서버는 어떻게 처리하도록 설계돼 있는지. (①-2 처럼 종료를 끝내 다시 보내지 않는 동작이 의도된 것인지)
  3. 종료 틱 생성 시점의 경합 — 유형 ②처럼 종료 틱이 직전 틱이 아닌 두 틱 전을 복사해 시각이 역행하는 경우가 구조적으로 가능한지.
  4. 유령 트립 — 유형 ③처럼 종료와 동시에 새 TRIP_ID 가 채번되고 후속 데이터가 없는 경우가 정상 동작인지, 아니면 억제 대상인지.

9. 재현 쿼리

수집서버 측 DB에서도 동일하게 확인하실 수 있도록 점검 쿼리를 첨부합니다.

-- 트립별 START/END 정합성 분류
WITH t AS (
  SELECT trip_id, device_key, count(*) ticks,
         min(gps_seq) first_seq, max(gps_seq) last_seq,
         count(*) FILTER (WHERE trip_event=0) st_cnt,
         min(gps_seq) FILTER (WHERE trip_event=0) st_seq,
         count(*) FILTER (WHERE trip_event=2) en_cnt,
         max(gps_seq) FILTER (WHERE trip_event=2) en_last
  FROM ruc.prim_rawgps
  WHERE device_key <> 'CAR000197'          -- 합성 시드 데이터 제외(1절 참고)
  GROUP BY 1,2)
SELECT CASE
         WHEN st_cnt <> 1 OR st_seq <> first_seq THEN 'A. START 이상'
         WHEN en_cnt = 0                          THEN 'B. END 없음'
         WHEN en_cnt > 1                          THEN 'C. END 복수'
         WHEN en_last <> last_seq                 THEN 'D. END 이 마지막 틱 아님'
         ELSE 'OK'
       END AS 분류,
       count(*) AS 트립수
FROM t GROUP BY 1 ORDER BY 1;

-- 종료 틱이 몇 틱 전을 복사했는지(정상=1, 2 이상이면 시각 역행 의심)
WITH e AS (SELECT trip_id, gps_seq, gps_dt, gps_lat, gps_lon
             FROM ruc.prim_rawgps
            WHERE trip_event = 2 AND device_key <> 'CAR000197')
SELECT e.trip_id, e.gps_seq AS end_seq,
       e.gps_seq - (SELECT max(p.gps_seq) FROM ruc.prim_rawgps p
                     WHERE p.trip_id = e.trip_id AND p.gps_seq < e.gps_seq
                       AND p.gps_dt = e.gps_dt
                       AND p.gps_lat = e.gps_lat AND p.gps_lon = e.gps_lon) AS 복사간격
FROM e ORDER BY 3 DESC NULLS FIRST, 1;

-- 유령 트립(직전 운행 마지막 틱과 시각·좌표가 같은 1틱 트립)
SELECT DISTINCT a.trip_id AS 유령트립, b.trip_id AS 직전운행, a.gps_dt, a.gps_lat, a.gps_lon
--     ^ 직전 운행의 마지막 두 틱(본 틱 + 종료 틱)이 동일값이라 조인이 2행으로 늘어난다
FROM ruc.prim_rawgps a
JOIN ruc.prim_rawgps b
  ON b.device_key = a.device_key AND b.trip_id <> a.trip_id
 AND b.gps_dt = a.gps_dt AND b.gps_lat = a.gps_lat AND b.gps_lon = a.gps_lon
WHERE a.trip_event = 0
  AND a.device_key <> 'CAR000197'
  AND (SELECT count(*) FROM ruc.prim_rawgps c WHERE c.trip_id = a.trip_id) = 1;
